## Featured Projects

<details>
<summary><b>OQART — Multi-Vendor E-Commerce Platform</b></summary>

<br/>

A multi-vendor commerce platform architected and built from the ground up, supporting the full merchant lifecycle: vendor onboarding, product catalog, inventory, order lifecycle, coupons, promotions, and payment workflows.

| | |
|:---|:---|
| **Stack** | Golang · PostgreSQL · Redis · Next.js · React Native · AWS · Docker |
| **Scale** | 70+ active sellers, full catalog and order lifecycle in production |
| **Performance** | Caching layers, asynchronous processing, and database-level optimisation across hot paths |
| **Security** | Authenticated vendor boundaries, role-scoped seller operations, secure payment workflow handling |
| **Impact** | Reusable backend services consumed across modules, reducing duplicated implementation by ~40% |
| **Repository** | [oqart.com](https://oqart.com) |

The platform is organised around clearly separated backend modules — inventory, order processing, pricing, promotions, and seller operations — each owning its data and exposing contracts consumed by the rest of the system. The core architectural decision was to extract the logic shared across those modules into reusable services rather than reimplementing it per feature, which cut duplicated implementation by roughly 40% and made subsequent modules substantially cheaper to build.

Performance work focused on the database first: schema design and indexing shaped to the actual query patterns, then caching for read-heavy paths, then asynchronous processing to move non-critical work off the request path. Client applications in Next.js and React Native are built against the same API contracts, developed in collaboration with product, design, and QA to reach production-ready quality.

</details>

<details>
<summary><b>Enterprise SaaS Backend Platform — Taskar Global</b></summary>

<br/>

A production backend platform serving a 10k+ user base with 2k+ daily actives, built on NestJS with Clean Architecture boundaries and deployed as containerised services on AWS.

| | |
|:---|:---|
| **Stack** | NestJS · Node.js · TypeScript · PostgreSQL · Redis · Docker · AWS ECS |
| **Scale** | 10k+ registered users · 2k+ daily active users |
| **Performance** | Redis caching, SQL query optimisation, `Promise.all()` parallelisation, transactional writes |
| **Security** | JWT authentication, RBAC, reusable Guards / Pipes / Interceptors, centralised exception handling, distributed rate limiting |
| **Impact** | Significant response-time reduction and lower infrastructure cost at equivalent load |
| **Repository** | Private — architecture discussed on request |

The service layer follows Clean Architecture and SOLID boundaries, keeping domain logic independent of transport and persistence concerns so modules stay individually testable and replaceable. Cross-cutting behaviour — authorisation, validation, error shaping — lives in reusable Guards, Pipes, and Interceptors rather than being repeated per controller, with every endpoint documented through Swagger.

Performance engineering combined Redis caching, query optimisation against measured slow paths, parallelised independent I/O, and database transactions for correctness under concurrency — together reducing response times materially while lowering infrastructure spend. The platform runs as Docker containers on AWS ECS and EC2 with RDS, S3, ECR, Lambda, and an Application Load Balancer, released through automated CI/CD pipelines.

Real-time and background capability sits alongside the request path: WebSocket services for live features, Cron-driven background processing, secure direct-to-S3 file uploads, Redis-backed distributed rate limiting, and automated PDF generation via Puppeteer. Grafana provides monitoring and logging so production behaviour is measured rather than inferred.

</details>

<details>
<summary><b>Monolith → Microservices Login Migration — Tata 1mg</b></summary>

<br/>

A zero-downtime extraction of the authentication module out of a large production monolith and into a standalone microservice, executed with the Strangler Fig Pattern against live consumer healthcare traffic.

| | |
|:---|:---|
| **Stack** | Python · REST APIs · Docker · Git · Jira |
| **Scale** | Live production traffic on a national consumer healthcare platform |
| **Performance** | Progressive rollout — 5% of production users routed to the new service |
| **Security** | Modular authentication and user management with preserved session and identity guarantees |
| **Impact** | Zero downtime throughout migration; established the path for further monolith decomposition |
| **Repository** | Private — architecture discussed on request |

Login is the highest-risk module to move, because every user meets it before anything else. The Strangler Fig approach let the new microservice run beside the monolith with a routing layer deciding which implementation served each request, so the migration could be validated against real traffic at 5% before widening — and reversed instantly if behaviour diverged.

The service exposes modular RESTful APIs in Python for authentication and user management, designed so that identity semantics remained byte-for-byte compatible with the monolith's existing contract. Containerisation, version control, and delivery tracking ran through Docker, Git, and Jira across a cross-functional release process.

</details>
